プログラミング言語には、2つのことについての規則が必要です。プログラムをどう書くか、そしてそれが何を意味するかです。`2 + 3 * 4` という式は、通常の乗算の優先順位に従うことも、厳密に左から右へ評価することもできます。どちらかに決めるまでは、結果を何と照らし合わせればよいかがありません。規則が決まれば、それをテストに書き、そのテストを実装の指針にできます。

テスト駆動開発（TDD）はこのように進めます。次の振る舞いについて自動テストを書き、それが想定どおりの理由で失敗することを確認してから、テストが通るまでコードを書きます。テストが Green になったら、振る舞いを変えずにコードの構造を整理できます。

以下では、インタプリタの小さな部品を例にこの流れを追います。例は擬似コードで書くので、アルゴリズムとテストを特定の言語やテストフレームワークに縛らずに示せます。

## 字句解析器（レクサー）から始める

次のソースコードを考えます。

```text
12 + 3
```

インタプリタがこれを扱うには、まず文字列を個々の要素に分ける必要があります。数値の `12`、記号の `+`、数値の `3` です。これらの要素をトークンと呼び、トークンを取り出すプログラムの部分を字句解析器（レクサー、スキャナー）と呼びます。出力は次のように書きます。

```text
[NUMBER(12), PLUS, NUMBER(3)]
```

レクサーは足し算をしません。次の段階であるパーサーが式の構造を決め、評価は構文解析の後に行われます。つまり、トークンの確認と、結果が `15` になることの確認は別の作業です。トークンの取り出しについては、Robert Nystrom が [『Crafting Interpreters』の Scanning の章](https://craftinginterpreters.com/scanning.html) で解説しています。

ここで扱うのは数値、プラス記号、空白だけです。それでも、不正な入力とリファクタリングを含めて TDD のサイクルを何周か回すには十分です。実際の言語では、変数名や文字列などの構文にもそれぞれ規則が必要になります。

## テストを先に書くと何が変わるか

レクサーがまだなくても、呼び出し方は決められます。

```text
tokenize("12 + 3")
```

この関数はソーステキストを受け取り、トークンのリストを返すか、エラーを報告します。このテストには、プログラムの実行もマシンコードの生成もファイルシステムも必要ありません。テストを先に書くと、内部がまだ何もない段階でコンポーネントの境界が決まります。

ユニットテストはプログラムの小さな部分を確認するもので、実装の後に書くこともできます。TDD が定めるのは作業の順序です。次の振る舞いを選び、そのテストを書き、テストを通し、構造の改善が必要かを確認します。

コードより先にテストを書くやり方は test-first と呼ばれます。TDD はこれに短いステップとリファクタリングを加えたものです。

現在の TDD の実践は、Kent Beck、Extreme Programming、そして Beck の2002年の著書『Test Driven Development: By Example』に由来します（[出版社の書籍ページ](https://www.informit.com/store/test-driven-development-by-example-9780321146533)）。

## TDD のサイクル

1. **Red.** 次の振る舞いのテストを書き、想定どおりの理由で失敗することを確認する。
2. **Green.** 新しいテストと既存のテストがすべて通る実装を追加する。
3. **Refactor.** コードやテストに簡素化できる箇所がないか確認し、振る舞いを変えずに簡素化して、テストを再実行する。

テストが赤になったという事実だけでは、ほとんど何も分かりません。関数がない、間違った値を返した、テストの準備が壊れている、のどれでもテストは失敗します。実装に手を付ける前に、失敗の原因を読みます。

*図1. TDDサイクルと段階間の遷移。*

新しいテストが最初から通った場合、失敗させるためにコードを壊す必要はありません。意図した振る舞いをテストしているか、その振る舞いがすでに実装されていないかを確認します。そうしたテストもリグレッションの防止には役立ちますが、新しいコードを書く理由にはなりません。

リファクタリングはすべてのテストが Green のときだけ行い、振る舞いの変更と構造の変更が同じステップに入らないようにします。簡素化するものがなければ、次の例に進みます。

## 最初のテスト：整数

例の前提をいくつか決めます。数値は `0` から `9` までの1文字以上の数字です。負号と小数部はまだ扱いません。位置は 0 から数えます。算術は桁数に上限のない整数演算とし、固定幅の型を使う実装ではオーバーフロー時の扱いを別に決める必要があります。

`ASSERT` は実際の結果と期待値を比較します。2つのトークンリストは、順序、トークンの種類、値がすべて同じときに等しいとみなします。

最初のテストです。

```text
TEST "複数の数字が1つの数値を構成する"
    ASSERT tokenize("12") == [NUMBER(12)]
```

`tokenize` がまだないので、テストは関数が未定義であるという理由で失敗します。これが想定どおりの最初の失敗です。シグネチャを宣言しないとテストを実行できない環境では宣言だけを先に書き、そのうえで振る舞いがまだないことを確認します。

最初の Green には、定数を返すだけで十分です。

```text
FUNCTION tokenize(source)
    RETURN [NUMBER(12)]
```

この仮実装が通せるのは1つのテストだけです。`"12"` のテストでは、本物の解析とハードコードされた定数を区別できません。

2つ目のテストを追加し、まずこのバージョンに対して実行します。

```text
TEST "数値の値は入力テキストに依存する"
    ASSERT tokenize("3") == [NUMBER(3)]
```

返ってくるのは `NUMBER(3)` ではなく `NUMBER(12)` です。ここで数字を読む実装を書きます。

```text
FUNCTION tokenize(source)
    IF source is empty
        RETURN []

    value ← 0
    FOR each index i in source
        IF source[i] is not a digit from "0" to "9"
            ERROR UnexpectedCharacter(position = i)
        value ← value * 10 + digit_value(source[i])

    RETURN [NUMBER(value)]
```

`digit_value` は、検証済みの数字文字を 0〜9 の整数に変換します。これで両方のテストが通ります。空の入力には `[]` を返すので、`tokenize("") == []` のテストは最初から通ります。その振る舞いはすでにあるからです。

すべての関数を定数から始める必要はありません。ここでは、2つ目のテストがどの曖昧さを取り除くかを示すために使いました。アルゴリズムが明らかなら、最初から書いて適切な例で確認して構いません。

## 次のテスト：プラス演算子

ここまでは入力全体が1つの数値である必要がありました。次に演算子を加えます。

```text
TEST "プラス記号が2つの数値を分割する"
    ASSERT tokenize("12+3") ==
        [NUMBER(12), PLUS, NUMBER(3)]
```

現在のコードは `+` に到達すると `UnexpectedCharacter(position = 2)` を投げます。これが新しいテストに期待する失敗です。

レクサーは1つの数値を読む代わりに、入力を先へ進みながらトークンを集めるようにします。

```text
FUNCTION tokenize(source)
    tokens ← []
    i ← 0

    WHILE i < length(source)
        IF source[i] is a digit from "0" to "9"
            value ← 0
            WHILE i < length(source) AND source[i] is a digit
                value ← value * 10 + digit_value(source[i])
                i ← i + 1
            tokens.append(NUMBER(value))
        ELSE IF source[i] == "+"
            tokens.append(PLUS)
            i ← i + 1
        ELSE
            ERROR UnexpectedCharacter(position = i)

    RETURN tokens
```

内側のループは連続する数字を読み、`+` で止まります。`+` は外側のループが次の周回で処理します。`AND` は左から右へ評価されるので、文字列が終わった後に `source[i]` を読むことはありません。

テスト全体を実行します。単一の数値と空入力のテストは、新しいテストと一緒に通り続けるはずです。演算子の位置が正しいかはパーサーの、和の計算は評価の担当です。

## 空白と不正な入力

次の規則です。トークン間の半角スペースはトークンを生成しません。タブと改行は後回しにします。

```text
TEST "トークン間の空白はスキップされる"
    ASSERT tokenize("12 + 3") ==
        [NUMBER(12), PLUS, NUMBER(3)]
```

テストは位置 2 の空白で失敗します。エラー分岐の前に次を追加します。

```text
ELSE IF source[i] == " "
    i ← i + 1
```

これですべてのテストが通ります。空白は見つけたその場でスキップするので、他の文字の位置は元のままです。字句解析の前に空白をすべて削除すると、`"1 2"` が `"12"` になるという別のバグが生まれます。

2つの数値が分かれたままであることを確認するテストです。

```text
TEST "空白によって数値同士は結合されない"
    ASSERT tokenize("1 2") == [NUMBER(1), NUMBER(2)]
```

これは最初から通ります。レクサーは両方の数値を返します。数値が2つ並んだ式が正しいかどうかはパーサーが判断します。

エラーの場合にもテストが必要です。

```text
TEST "未知の文字は位置情報とともに拒否される"
    EXPECT ERROR UnexpectedCharacter(position = 2)
        tokenize("12@3")
```

エラー分岐は以前からあるので、このテストもすでに Green です。テストが確認するのはエラーの種類と位置で、メッセージの正確な文言ではありません。そのため、ユーザー向けの文言は後からテストを壊さずに改善できます。

## リファクタリング：数値の読み取りを抽出する

外側のループは今、2つの仕事をしています。トークンの種類を選ぶことと、数字を累積するアルゴリズムです。数値の読み取りを独立した関数に移すと、メインループは数値、プラス、空白、エラーのどれかを選ぶものとして読めるようになります。

補助関数は最初の数字の位置を受け取り、`(value, new_index)` を返します。

```text
FUNCTION read_number(source, i)
    value ← 0
    WHILE i < length(source) AND source[i] is a digit
        value ← value * 10 + digit_value(source[i])
        i ← i + 1
    RETURN (value, i)
```

リファクタリング後のレクサーです。

```text
FUNCTION tokenize(source)
    tokens ← []
    i ← 0

    WHILE i < length(source)
        IF source[i] is a digit from "0" to "9"
            (value, i) ← read_number(source, i)
            tokens.append(NUMBER(value))
        ELSE IF source[i] == "+"
            tokens.append(PLUS)
            i ← i + 1
        ELSE IF source[i] == " "
            i ← i + 1
        ELSE
            ERROR UnexpectedCharacter(position = i)

    RETURN tokens
```

同じテストを同じ期待値で実行します。戻り値の `i` を捨ててはいけません。捨てると、外側のループが同じ数値をもう一度読みます。

![リファクタリング時にテストが保護するもの](/img/tdd/ja/tdd-contract-ja.svg)

*図3. 公開された振る舞いと内部実装。*

このステップで言語の規則は増えていません。コードの構成が変わり、テストは変わっていません。補助関数を抜き出しても実装が分かりやすくならないなら、ループの中に残して構いません。リファクタリングの結果が新しい関数である必要はありません。

## 次に必要になるテスト

数値とプラス記号しか知らないレクサーは、言語にはまだ程遠いものです。それでも同じ方法は後続のコンパイラのどの段階にも使えます。最小の例を書き、分かりやすい理由で失敗するのを確認し、実装を広げます。

### レクサーの拡張：識別子とキーワード

数値と演算子の次に、言語には変数名とキーワード（`IF`, `RETURN`, `TYPE`）が必要です。次のテストは、英字の並びを識別子として読み、予約語を区別することをレクサーに求めます。

```text
TEST "キーワードは通常の識別子と区別される"
    ASSERT tokenize("return total") ==
        [RETURN, IDENTIFIER("total")]
```

現在のレクサーは英字を予期しない文字として拒否します。新しいコードは英字の並びを読み、キーワード表を引きます。契約は変わりません。文字列を入力し、トークンのリストを出力します。

### パーサー

レクサーは文法を確認しません。`"12++3"` はすべての文字が既知なので、`PLUS` が2つ続くトークン列になります。その並びが文法上許されるかを決めるのはパーサーです。

文法が2つの数値の二項加算だけを許す場合、パーサーのテストは次のように始められます。

```text
TEST "2つの数値の加算がASTノードを構築する"
    ASSERT parse([NUMBER(12), PLUS, NUMBER(3)]) ==
        Add(Number(12), Number(3))

TEST "不完全な式は構文エラーとして拒否される"
    EXPECT ERROR SyntaxError(expected = "expression", position = 2)
        parse([NUMBER(12), PLUS])
```

`Add(Number(12), Number(3))` は構文木（AST）を表し、演算とそのオペランドを示します。入力はトークンのリストで、出力は AST のノード、または不完全な部分の位置を持つ構文エラーです。後で掛け算を加えるなら、優先順位の規則と `2 + 3 * 4` のような例も一緒に必要になります。通常の優先順位では、木の中で掛け算が足し算より下に置かれ、評価結果は `14` になります。この例はインタプリタの複数の部分をまとめて動かします。レクサー自体のテストは引き続きトークンだけを確認します。

### 意味解析と型検査

構文的に正しい木でも意味をなさないことがあります。たとえば数値と文字列を足す場合や、宣言されていない関数を呼ぶ場合です。型とスコープの検査は完成した AST に対して行います。

```text
TEST "オペランドの型不一致は型エラーを発生させる"
    tree ← Add(Number(12), Text("abc"))
    EXPECT ERROR TypeError(expected = "Number", found = "Text", position = 1)
        check_types(tree)

TEST "未宣言の関数呼び出しは拒否される"
    tree ← Call(name = "helper")
    EXPECT ERROR UndeclaredSymbol(name = "helper", position = 0)
        check_scopes(tree)
```

テストは木を渡し、得られた型か、ソース上の位置を持つエラーを確認します。シンボルテーブルがフラットなリストか、マップか、スコープのチェーンかには関知しません。

### 静的解析とリンター

リンターの規則は、コンパイルを止めずに、疑わしいコードや冗長なコードを警告します。未使用の型、読まれない構造体フィールド、到達不能なコードなどです。

```text
TEST "未使用の型定義は警告を生成する"
    program ← DeclareType(name = "Point", fields = ["x", "y"])
    ASSERT collect_warnings(program) ==
        [Warning(code = "W1003", position = 0)]
```

テストはプログラム（またはプログラムについて集めた事実）を渡し、警告のリストを確認します。

どの段階でも、テストが見るのは入力データと、期待される出力または診断コードだけです。そのため、リファクタリングの際に内部のアルゴリズム、テーブルの構成、中間形式をテストを書き直さずに変更できます。

## テストが実装の変更をどう支えるか

レクサーのテストが知っているのは、引数、結果、失敗の仕方です。ループがいくつあるか、どの関数が数値を累積しているかは知りません。だから `read_number` を抽出してもテストを変更する必要はありませんでした。

テストが内部メソッドをちょうど1回呼ぶことを要求していたら、そのメソッドを移動したり統合したりしたときに、レクサーが正しいトークンを返していてもテストが壊れる可能性があります。そうした期待を加える前に、その呼び出し自体が要件の一部かを判断します。要件である場合もあります。たとえば外部システムとのやり取りで、失敗後にリクエストを2回送ってはならない場合です。そうしたケースでは依存の制御可能な代替が役立ち、モックはやり取りへの期待をテストで設定できる代替の一種です。私たちのレクサーには、文字列と期待される結果があれば足ります。

時刻、乱数、ネットワーク、ファイルシステムはテストを不安定（flaky）にすることがあります。言語の規則がそのどれかに依存するなら、テストが既知の値を渡せるように明示的に受け渡し、実際の依存は別にテストします。

## Green のテストが保証しないこと

テストが確認するのは、開発者が書き留めた規則です。開発者が誤った優先順位を選び、同じ規則をテストとコードの両方に書けば、テストは通ります。その規則が言語の作者の意図に合っているかは、別に議論する必要があります。

1つの例ですべての入力を網羅することはできません。`"12@3"` のテストが示すのは、この文字がこの位置で拒否されることです。不正なプログラムがすべて正しく扱われることまでは示しません。空入力、先頭や末尾の不正な文字、長い数値などには、テストを増やしていく中でそれぞれ専用のテストが必要です。

コードカバレッジは、テスト中にどのコードが実行されたかを示します。結果が確認されたかどうかは何も示しません。レクサーを呼び出してすべての分岐を通っても、返されたトークンを一度も比較しないことは可能です。

ミューテーションテスト（変異テスト）は、プログラムに意図的な小さい変更を加え、テストがそれに気づくかを調べます。数値の読み取りで `10` の代わりに `1` を掛けると、`"12"` は `3` になります。複数桁の数値のテストはこの変更を検出し、1桁のテストは見逃します。生き残った変異は確認が必要です。すべての正しい入力に対して元のプログラムと等価な場合があるからです。この確認をせずにスコアを追っても意味がありません。また、ミューテーション解析は多数の改変版をテストするため、通常のテスト実行よりコストがかかります。検出された変異、生き残った変異、等価な変異の違いは [PIT mutation testing のドキュメント](https://pitest.org/quickstart/basic_concepts/) で説明されています。

## サイクルが負担になる場面

TDD には、テストできる程度に正確に記述できる次の結果が必要です。パーサー、計算、アクセス規則、データ変換は、多くの場合この条件を満たします。再現できるバグも同じで、プログラムが誤動作する入力が出発点になります。

なじみのないライブラリを調べている段階や、どんなインターフェースが使いやすいかをまだ探っている段階では、期待される振る舞いがまだ存在しないことがあります。そこでは使い捨てのプロトタイプが役立ちます。調査が終わったら、それを捨てるか、決めた振る舞いをテストで固定してから先へ進みます。

UI の見た目、アニメーションの感触、ハードウェアの挙動には、別の確認方法が必要です。ただし、そうしたシステムの中にある決定論的な規則は、テストファーストで作れます。

適したタスクでも、テストのたびにネットワークを待ったりアプリケーション全体を起動したりすると、サイクルは遅くなります。計算や規則は単独でテストし、インフラとの連携は CI の統合テストに任せます。不安定なテストは、結果を直前の変更と結び付けられないので、先に直す必要があります。

1つのテストを通そうとしている途中で隣のコードまで作り直し、複数のテストが落ちると、原因を見つけにくくなります。ステップが小さければ、疑うべき箇所も少なくて済みます。

## 公開された研究の結果

TDD の研究に出てくる割合は、それぞれ特定の課題、参加者、比較方法に基づくものです。品質を見つかった欠陥で測る研究もあれば、外部テストの合格率で測る研究もあります。また、初期実装の時間は、製品の寿命全体のコストと同じではありません。

Nagappan らは、Microsoft の3チームと IBM の1チームのプロジェクトを、TDD を使わない類似プロジェクトと比較しました。欠陥密度は約 40〜90% 低下したと報告されています。初期開発時間の 15〜35% の増加はチームの管理者による見積もりで、統制された実験で測定されたものではありません。結果は4つの具体的なプロジェクトから得られたもので、任意のチームにそのまま当てはまるものではありません。[Nagappan et al., Empirical Software Engineering](https://doi.org/10.1007/s10664-008-9062-z) （[Microsoft Research レポート](https://www.microsoft.com/en-us/research/wp-content/uploads/2009/10/Realizing-Quality-Improvement-Through-Test-Driven-Development-Results-and-Experiences-of-Four-Industrial-Teams-nagappan_tdd.pdf)）。

George と Williams は、ペアで作業する24名のプロ開発者を対象に実験を行いました。TDD グループの成果物は外部テストケースに 18% 多く合格し、作業時間は 16% 長くかかりました。課題は小規模で、対照群の開発者の多くは実装後に書くよう求められた自動テストを書きませんでした。そのため、同じ程度に完全なテストを前提とした2つの順序の純粋な比較とは言えません。[George and Williams, Information and Software Technology (Elsevier)](https://doi.org/10.1016/S0950-5849(03)00204-0)。

Rafique と Mišić による27件の研究のメタ分析では、外部品質に小さな改善効果が見られ、生産性への影響はほとんどないか判別できませんでした。産業界の研究では、学術的な研究よりも品質の改善と初期の生産性の低下がともに大きく現れました。[Rafique and Mišić, IEEE Transactions on Software Engineering](https://doi.org/10.1109/TSE.2012.28)。

Fucci らはプロセスそのものを調べ、39名のプロ開発者について82件の観察を分析しました。外部品質と生産性に主に関連していたのは小さく均一なステップで、テストをコードの前に書くか後に書くかはほとんど影響しませんでした。これは観察された関連であり、改善の原因を証明するものではありません。[Fucci et al., IEEE Transactions on Software Engineering](https://doi.org/10.1109/TSE.2016.2616877)。

Ghafari らは、研究によって結果が食い違う理由を調べました。[Ghafari et al., arXiv](https://arxiv.org/abs/2007.09863)。

TDD は欠陥のコストが高い領域で検討する価値があります。ただし、これらの研究のどれも、チームに特定のバグ削減や高速化を約束する根拠にはなりません。初期開発とその後の修正を分けて、自分たちの作業で効果を測る必要があります。

## 既存のプロジェクトで始める

小さく決定論的な部分から始めます。計算、バリデーション、再現できるバグなどです。そのテストがローカルで実行でき、結果を信頼できることを確認します。

バグ修正では、まずそのバグを再現するテストを追加します。古いコードで実行し、失敗の理由を読みます。次にバグを修正し、周辺のテストと一緒に再実行し、その後で初めて触れたコードを整理します。このテストは、同じバグの再発を防ぐチェックとして残ります。

新しい振る舞いでは、ケースの短いリストを作り、最初の1つを選びます。ペアで作業するときは、次のテストがどの曖昧さを取り除き、実装にどんな変更を求めるかを話し合います。

チームで試験運用をする場合は、開始前と後で同じ方法で測れる指標を使い、開始前の基準値を記録しておきます。

| 指標 | 目的 |
| --- | --- |
| リリース後の欠陥と再発するリグレッション | 成果物の品質が変わるかを確認する |
| ローカルテストの実行時間と不安定なテストの割合 | 小さな変更後のフィードバックが速いままかを確認する |
| タスクの所要時間とリグレッション調査の時間 | 実装のコストとデバッグのコストを分ける |
| コードカバレッジとミューテーションテストのスコア | 実行されているが確認が弱いコードを見つける |

4〜8週間後に最初の振り返りを行います。この期間は運用上の取り決めで、それだけで結論に十分なデータが集まるとは限りません。タスクごとの違いを考慮し、テストがどこで役立ち、テストの準備や実行がどこで妨げになったかを開発者に聞きます。数値はプロセスの調整に使い、開発者の評価には使いません。

高速なテストは小さな変更のたびに実行し、重い統合テストとエンドツーエンドテストは CI の別ステージに置きます。その場合も、リリースが依存するチェックは必須のままにします。ミューテーション解析は重要なモジュールから始めるのがよいでしょう。

コードレビューでは、要件からコードまでの道筋をたどります。実装がどんな結果を約束し、テストがそれをどう確認し、テストがどんな違反を検出できるかです。このつながりを説明しにくいなら、要件とテストの期待値を明確にします。
